# ULBC极低码率编解码器研究报告初版思路

## 一、项目定位

ULBC 3GPP正在讨论极低码率语音编解码器。国内手机芯片厂商如果要在中国国内立项开展极低码率编解码器研究，建议不要将项目定位为单纯跟踪3GPP ULBC进展，而应定位为：

> **面向卫星通信和极弱网语音业务的超低码率编解码器评价体系、约束条件与标准化路径研究。**

这样既可以承接3GPP ULBC的国际标准化方向，又可以体现中国星网作为卫星通信运营商提供的真实业务场景、网络约束和行业需求，同时发挥手机芯片厂商在端侧部署、复杂度、功耗和工程实现方面的优势。

建议项目总体定位为：

> **以3GPP ULBC为国际标准化参考，以中国星网卫星通信业务需求为场景输入，以手机芯片端侧部署能力为工程约束，研究适合国内卫星通信和极弱网语音业务的极低码率编解码器评价体系、技术要求和标准化路径。**

---

## 二、对原始思路的评价

### 1. “先标准化评价方式”是正确的

这一点非常关键。ULBC不是简单地把EVS、AMR-WB一类传统语音编解码器继续压低码率，而是在极低码率下重新分配信息优先级。

传统语音编码评价中，ACR、DCR、CCR等通常是主观听音评价方法，评价结果可以体现为MOS、DMOS或CMOS。PESQ、POLQA、STOI、ESTOI等则属于客观评价方法，用于预测语音质量、可懂度或相关感知指标。

因此，原始表述中“客观的是MOS，主观的是ACR/DCR”建议修改为：

> 主观评价可以采用ACR、DCR、CCR等方法形成MOS、DMOS或CMOS结果；客观评价则采用可重复计算的指标来预测语音质量、可懂度、说话人相似度或语义保持程度。

在极低码率条件下，语音编解码器很难同时保持高自然度、高说话人相似度、高可懂度和低复杂度。因此，需要首先建立分层评价体系，明确不同业务场景下“语义可懂度、自然度、说话人保持、鲁棒性、时延、复杂度”的优先级。

你提出“极低码率下语义可懂度优先于说话人保持”，整体是合理的，但建议不要写成绝对结论，而应写成需要研究报告验证和分级定义的设计假设。

不同业务场景下，信息优先级可能不同：

| 场景 | 优先级可能不同 |
|---|---|
| 应急通信、卫星窄带电话 | 可懂度、鲁棒性优先 |
| 普通人与人通话 | 可懂度和说话人可辨识都重要 |
| 政务、公安、调度、客服 | 说话人身份、语气、情绪可能也重要 |
| 机器辅助理解/ASR转写 | 语义和字词正确率优先 |

更稳妥的表述是：

> 在0.8–2.4 kbps等极低码率条件下，编解码器很难同时保持高自然度、高说话人相似度、高可懂度和低复杂度。因此研究报告应首先建立分层评价体系，明确不同业务场景下语义可懂度、自然度、说话人保持、鲁棒性、时延和复杂度的优先级。

---

### 2. “不同采样率、不同码率下定义质量”是正确的，但应加入“业务档位”

不同采样率、不同码率、不同复杂度下定义质量要求是必要的。但建议不要只按照8 kHz/16 kHz、码率、复杂度来分，而应按照业务档位组织。

例如：

| 档位 | 可能目标 | 典型约束 |
|---|---|---|
| 极限可用档 | 0.8 kbps左右，8 kHz，保证基本可懂 | 应急、弱覆盖、容量极限 |
| 基础通话档 | 1.2–2.4 kbps，8/16 kHz，较好可懂度 | 卫星语音、窄带运营 |
| 增强体验档 | 2.4–4.8 kbps，16 kHz，兼顾自然度和说话人 | 更接近普通语音通话体验 |

这样，中国星网可以贡献真实网络、容量、链路预算、丢包、抖动、RTT、业务并发等输入；手机芯片厂商可以贡献端侧复杂度、功耗、内存和部署能力输入。

---

### 3. “最后才选择模型”是正确的

这一点尤其重要。国内立项如果一开始就写“研究某个AI codec模型”，容易变成单纯算法课题；如果一开始写“跟踪3GPP ULBC”，又容易变成情报跟踪。

更合理的路线是：

> 先定义场景、评价、约束和测试方法，再评估候选技术路线，最后给出标准化建议。

也就是说，模型不是研究报告的起点，而是评价体系和约束体系下的验证对象。

---

## 三、建议修改后的初版思路

# 极低码率语音编解码器研究报告初版框架

## 1. 项目定位

本项目面向卫星通信、极弱网通信和未来6G语音业务，研究极低码率语音编解码器的技术需求、评价方法、设计约束、网络适应能力和标准化路径。

项目不应仅限于跟踪3GPP ULBC进展，而应结合国内卫星通信运营场景、终端芯片部署能力、弱网语音业务需求，形成可指导后续国内标准化工作的研究报告。

建议定位为：

> **以3GPP ULBC为国际标准化参考，以中国星网卫星通信业务需求为场景输入，以手机芯片端侧部署能力为工程约束，研究适合国内卫星通信和极弱网语音业务的极低码率编解码器评价体系、技术要求和标准化路径。**

---

## 2. 第一阶段：标准化评价体系研究

极低码率编解码器首先需要解决“如何评价”的问题。

传统语音编解码器主要关注编解码后语音与原始语音在整体听感上的接近程度，常见主观评价方法包括ACR、DCR、CCR等，评价结果通常体现为MOS、DMOS或CMOS。客观评价方法则尝试用算法预测主观质量。

但在极低码率条件下，编解码器无法同时完整保持语义内容、说话人特征、自然度、情绪、韵律和背景音。因此，评价体系应从单一“综合音质”扩展为多维评价。

| 评价维度 | 说明 |
|---|---|
| 语义可懂度 | 听者能否听清内容，是否影响基本通信 |
| 字词准确性 | 可结合人工转写或ASR结果评估 |
| 说话人可辨识度 | 是否还能分辨是谁在说话 |
| 语音自然度 | 是否机械、失真、生成感明显 |
| 韵律与情绪保持 | 语调、停顿、情绪是否被破坏 |
| 噪声与非语音鲁棒性 | 对背景噪声、音乐、环境声是否异常 |
| 弱网鲁棒性 | 丢包、抖动、长RTT下是否仍可通信 |
| 端侧复杂度 | CPU/NPU/DSP占用、内存、功耗、时延 |

其中，极低码率场景下建议重点研究一个核心问题：

> 在0.8 kbps、1.2 kbps、2.4 kbps等典型极低码率下，语义可懂度、说话人保持、自然度三者之间应如何排序？

初步建议是：

> 对卫星应急通信、极弱覆盖通信等场景，可懂度应优先于说话人相似度和自然度；但对普通人与人通话，不能完全牺牲说话人辨识度，需要定义最低可接受门限。

---

## 3. 第二阶段：业务场景和质量档位研究

研究报告应结合中国星网的业务输入，定义不同卫星通信场景下的质量目标。

建议至少区分三类业务场景：

| 场景 | 目标 | 编码器关注点 |
|---|---|---|
| 应急保底通信 | 能听懂、能完成指令传达 | 极低码率、强鲁棒性、低功耗 |
| 普通卫星语音 | 接近可接受通话体验 | 可懂度、自然度、时延平衡 |
| 行业调度/专网语音 | 稳定、可靠、可识别 | 可懂度、说话人辨识、弱网恢复 |

在此基础上，再定义8 kHz/16 kHz、不同码率、不同帧长下的质量要求，而不是单纯从技术参数出发。

建议研究的参数包括：

| 参数 | 需要研究的问题 |
|---|---|
| 采样率 | 8 kHz是否作为基础强制能力，16 kHz是否作为增强能力 |
| 码率 | 0.8/1.2/2.4/4.8 kbps各自适合什么业务 |
| 帧长 | 20/40/80/160 ms对压缩效率、时延、PLC的影响 |
| 算法延迟 | GEO卫星高RTT下，编解码器还能接受多少额外延迟 |
| 复杂度 | 手机AP CPU、DSP、NPU、低端终端分别能承受多少 |
| 内存 | 模型大小、运行时buffer、状态缓存如何限制 |
| 功耗 | 长时间卫星语音通话下是否可接受 |
| 鲁棒性 | 丢包、抖动、乱序、突发丢包下的退化曲线 |

---

## 4. 第三阶段：弱网、FEC、PLC和系统能力研究

极低码率语音编码不能只看干净信道下的音质。卫星通信中，网络条件本身就是核心约束。

建议把FEC、PLC、DTX/CNG、jitter buffer、帧聚合等系统能力作为研究报告的重要内容，而不是附属内容。

需要重点研究：

| 方向 | 研究内容 |
|---|---|
| PLC | 丢1包、连续丢2包、连续丢3包以上时的质量退化 |
| FEC | 编码内FEC、应用层冗余、跨帧冗余的开销与收益 |
| 帧长 | 长帧有利于压缩，但不利于低时延和PLC |
| Jitter buffer | GEO长时延和抖动下，缓存策略如何影响体验 |
| DTX/CNG | 静音压缩是否能进一步降低平均码率 |
| 误码/坏帧 | AI codec面对bit error是否比传统codec更脆弱 |
| 速率自适应 | 是否需要0.8/1.2/2.4 kbps之间动态切换 |

这里可以形成一个重要判断：

> 对ULBC而言，编码器本体不是唯一标准化对象。端到端体验还依赖PLC、FEC、jitter buffer、DTX/CNG、码率切换和网络适配机制。因此研究报告应提出“编解码器+弱网适配”的整体评价方法。

---

## 5. 第四阶段：端侧部署约束研究

作为手机芯片厂商，端侧部署约束研究是区别于单纯运营商或高校研究的关键贡献。

研究报告应明确：

| 部署维度 | 需要标准化或至少形成建议的内容 |
|---|---|
| 模型大小 | 权重大小、Flash占用 |
| RAM占用 | 运行时buffer、隐藏状态、缓存 |
| 计算复杂度 | MACs、MCPS、CPU占用 |
| 推理时延 | 每帧推理时间，是否满足实时 |
| 硬件平台 | AP CPU、DSP、NPU、MCU级硬件的适配能力 |
| 功耗 | 连续通话功耗，是否适合手机/卫星终端 |
| 初始化时间 | 模型加载、首帧时延 |
| 可移植性 | C/C++实现、定点化、TFLite/ONNX/自研runtime支持 |
| 安全与隐私 | 端侧运行是否避免语音上传云端 |

这部分建议不要只写“复杂度越低越好”，而要形成分档：

| 模型档位 | 目标 |
|---|---|
| 极低复杂度模型 | 适合低端卫星终端、MCU/DSP级部署 |
| 主流终端模型 | 适合手机AP CPU/DSP/NPU部署 |
| 增强模型 | 适合高算力终端或下行解码侧复杂度更高的场景 |

---

## 6. 第五阶段：候选ULBC技术路线研究

在评价体系、业务需求、复杂度约束明确后，再研究候选模型。

候选技术路线可以包括：

| 技术路线 | 研究重点 |
|---|---|
| 传统参数编码增强 | 低复杂度、稳定、可解释，但极低码率质量有限 |
| 神经声码器 | 低码率下自然度较好，但复杂度和鲁棒性需评估 |
| 语义编码 | 可懂度潜力大，但说话人和自然度可能损失 |
| RVQ/残差量化 | 适合离散token表达，可做码率分层 |
| 熵编码 | 进一步降低平均码率，但复杂度和时延需评估 |
| 生成式解码 | 可在低码率下生成自然语音，但需控制幻觉和内容错误 |
| 混合编码 | 语义、韵律、说话人、残差信息分层传输 |

建议不要一开始指定唯一模型，而是提出：

> 研究报告应基于统一测试集、统一评价指标、统一复杂度统计方法，对多个候选ULBC技术路线进行横向评估，并给出适合不同业务档位的推荐方案。

---

## 7. 第六阶段：标准化推进建议

最终报告产物应服务于后续标准化，所以不只是“技术综述”，而应输出可执行建议。

建议最终形成以下成果：

1. **ULBC业务场景定义**  
   包括卫星应急通信、普通卫星语音、行业调度、极弱网通信等。

2. **ULBC评价体系建议**  
   包括可懂度、自然度、说话人保持、弱网鲁棒性、复杂度、功耗等多维指标。

3. **ULBC测试方法建议**  
   包括测试语料、语言覆盖、噪声条件、丢包模型、抖动模型、主观听音方法和客观预测方法。

4. **ULBC技术约束建议**  
   包括采样率、码率、帧长、算法延迟、复杂度、内存、功耗、部署平台。

5. **ULBC候选方案评估框架**  
   不限定单一模型，而是给出不同复杂度档位、不同业务档位的候选路线。

6. **国内标准化路线建议**  
   包括如何与3GPP ULBC保持同步，哪些部分适合形成国内研究报告，哪些部分未来可进入行业标准或团体标准。

---

## 四、建议形成的初版结论

本研究不应仅作为3GPP ULBC进展跟踪，而应面向国内卫星通信和极弱网语音业务，建立极低码率语音编解码器的评价体系、业务需求、技术约束和标准化路径。

第一，研究报告应优先解决评价标准化问题。传统语音编码主要以整体语音质量为核心评价目标，但在0.8–2.4 kbps等极低码率下，编解码器需要在语义可懂度、说话人保持、自然度、复杂度和弱网鲁棒性之间做取舍。因此，应建立多维评价体系，并根据应急通信、普通卫星语音、行业调度等不同场景定义不同优先级。对于极弱网和应急通信场景，可懂度应作为最高优先级，但普通人与人通话仍需定义说话人可辨识度和自然度的最低要求。

第二，在评价体系明确后，应进一步研究不同采样率、码率、帧长和网络条件下的质量档位。研究内容应覆盖8 kHz/16 kHz采样率、0.8/1.2/2.4/4.8 kbps等码率、20/40/80/160 ms帧长，以及算法延迟、端侧复杂度、内存、功耗等部署约束。同时，应结合中国星网提供的卫星通信网络特性，研究丢包、抖动、长RTT、弱覆盖等条件下FEC、PLC、DTX/CNG和jitter buffer对端到端语音体验的影响。

第三，在业务需求、评价方法和工程约束明确后，再对候选ULBC模型和技术路线进行评估。候选方案不应只选择单一模型，而应根据不同硬件能力和业务档位，研究极低复杂度模型、主流终端模型和增强体验模型等多种方案。最终报告应输出面向国内标准化的评价方法、测试方法、技术约束、候选方案评估框架和标准化推进建议，为后续ULBC相关标准制定提供航标。

总体来说，该初版逻辑比单纯“跟踪3GPP ULBC”更完整，也更适合国内立项：

> **3GPP负责国际方向，中国星网提供场景和网络约束，手机芯片厂商提供端侧部署和复杂度约束，研究报告负责把这些内容转化为标准化语言。**
